The lab, step by step

Run these in order from the project root. Each step says what you should see and why it matters.

  1. 1

    Check the cluster is ready

    Containers are replaceable, so confirm Minikube is running before creating anything.

    minikube status
    kubectl get nodes

    Expect: the node shows Ready.

  2. 2

    Create the emptyDir Pod

    day8-emptydir-pod runs BusyBox and mounts an emptyDir volume at /cache. The volume lives exactly as long as the Pod.

    kubectl apply -f k8s/emptydir-pod.yaml
    kubectl describe pod day8-emptydir-pod

    Expect: status Running and a /cache mount in the description.

  3. 3

    Request storage with a PVC

    The claim day8-storage-pvc asks for 1Gi. Kubernetes binds it to a matching PersistentVolume, or provisions one through the default StorageClass.

    kubectl apply -f k8s/pvc.yaml
    kubectl get pvc

    Expect: STATUS Bound. If it stays Pending, run kubectl describe pvc day8-storage-pvc and read the Events.

  4. 4

    Mount the claim and verify the data

    day8-storage-pod mounts the claim at /data. Check the real file inside the running container, not just the Pod status.

    kubectl apply -f k8s/storage-pod.yaml
    kubectl exec day8-storage-pod -- cat /data/message.txt

    Expect: the message text prints. If the file is missing, write one first with kubectl exec day8-storage-pod -- sh -c 'echo "Hello" > /data/message.txt'.

  5. 5

    Run the lifecycle experiment

    Write a file, delete the Pod, recreate it, and compare. A container restart alone keeps emptyDir data; deleting the Pod does not.

    kubectl exec day8-emptydir-pod -- sh -c 'echo test > /cache/test.txt'
    kubectl delete pod day8-emptydir-pod
    kubectl apply -f k8s/emptydir-pod.yaml
    kubectl exec day8-emptydir-pod -- ls -la /cache

    Expect: test.txt is gone. Repeat with the storage Pod and /data; the file stays because the PVC remains.

  6. 6

    Document and publish

    Keep manifests, docs, and this showcase in version control.

    git add README.md docs/ k8s/ showcase/
    git commit -m "Rebuild Day 8 storage showcase"
    git push

Two Pods, two lifecycles

Same kind of container, different storage. The difference is who owns the data.

Temporary

emptyDir

Podday8-emptydir-pod
mounts at /cache
Ephemeral volumeemptyDir

Created when the Pod is scheduled. Containers in the Pod can share it, and it survives container restarts. It is deleted when the Pod is removed.

Persistent

PersistentVolumeClaim

Podday8-storage-pod
mounts at /data
Claimday8-storage-pvc, 1Gi
binds to
Backing resourcePersistentVolume

The claim is its own object. Deleting the Pod leaves the claim and its data in place, subject to the reclaim policy of the volume.

Production note

A PVC is not a backup. Durability depends on the storage driver, access mode, reclaim policy, and workload setup. Plan backups and recovery separately.

The YAML files

Reference versions of the three manifests. Your files in k8s/ are the source of truth, so compare before applying.

Defines a BusyBox Pod with a temporary volume at /cache
apiVersion: v1
kind: Pod
metadata:
  name: day8-emptydir-pod
spec:
  containers:
    - name: busybox
      image: busybox
      command: ["sleep", "3600"]
      volumeMounts:
        - name: cache-volume
          mountPath: /cache
  volumes:
    - name: cache-volume
      emptyDir: {}
Requests 1Gi of storage
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: day8-storage-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
Mounts the claim at /data
apiVersion: v1
kind: Pod
metadata:
  name: day8-storage-pod
spec:
  containers:
    - name: busybox
      image: busybox
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data-volume
          mountPath: /data
  volumes:
    - name: data-volume
      persistentVolumeClaim:
        claimName: day8-storage-pvc
